# Aegis — design of record

What is decided about this runtime, and why. `AGENTS.md` is the contract for coding agents (scope,
code rules); `COS.md` holds the rules of the operating mode; `README.md` and `docs/` are the user
guide. Code comments cite sections of this file by number (`PLAN 7.13`) and by their bold lead-ins
(`§ 7.6 *Authoring*`): amend sections in place, and keep the numbers and lead-ins.

§ 1–6 describe the MVP (Phases 0–10, landed). § 7 is what came after it: the seams the MVP kept
open, the post-MVP phases (11–19, landed), the slices that are not phases (§ 7.10–7.19,
landed), and three surfaces that are not scheduled (§ 7.7–7.9).

Stack is fixed: Tauri 2 + TypeScript + React + Vite, a Rust runtime in `src-tauri`, pnpm, Rust
edition 2021. The WebView renders UI only — the agent loop, tool execution, secrets and policy live
in Rust.

---

## 1. Repo tree

The layout is in `docs/architecture.md`. Three structural decisions:

- `src/ipc/bindings.ts` is generated by `ts-rs` from the Rust payload types during `cargo test`. One
  source of truth for IPC shapes; the TS side never hand-writes one.
- Tools are name-keyed behind one `ToolSpec` registry, so an MCP client registers external tools into
  the same registry without touching the turn loop or the policy layer (Phase 18 did exactly that).
- `agent/turn.rs` talks to a `Provider` trait and to the registry. One loop, not one per agent,
  provider or domain.

## 2. Tauri commands and events

Commands are `domain_verb`, events are `domain:verb`. Payloads are Rust structs exported to
`src/ipc/bindings.ts`, `snake_case` on the wire; that file is the reference for shapes.

### 2.1 Commands (`invoke`)

| --- | --- | --- |
| Projects | `project_pick_workspace`, `project_create`, `project_list`, `project_open`, `project_delete`, `project_list_exec_hosts`, `project_set_exec_host` | The folder dialog runs in Rust; the WebView holds no `dialog:` permission. A workspace path is canonicalized once, on the way in. Deleting a project forgets it and never touches the folder. Hosts: § 7.12 |
| Sessions | `session_create` (`project_id`, `title?`, `agent_id?`, `provider_id?`, `model?`), `session_set_binding` (`session_id`, `provider_id?`, `model?`), `session_list`, `session_open`, `session_rename`, `session_delete`, `session_send`, `session_cancel`, `session_compact` | `session_send` returns a `TurnHandle` once the turn is registered; everything after is events. Sending while running is `E_TURN_BUSY`. The identity is fixed at creation; the provider and model are an override of the identity's pair, refused while a turn runs, and both omitted inherits (§ 7.19). `session_compact` always returns the detail (a session too short to fold is an answer) and is refused while a turn runs |
| Approvals | `approval_list_pending`, `approval_resolve` (`allow_once` / `allow_session` / `deny`), `approval_grants`, `approval_revoke_grant` | An unknown or expired request is `E_APPROVAL_STALE` and the UI re-syncs. `allow_session` on a row offering no grant is `E_GRANT_NOT_ALLOWED`, enforced in Rust. | Connectors | `connector_list`, `connector_save`, `connector_delete`, `connector_set_enabled`, `connector_reconnect` | No tool installs a connector (Phase 18) |
| Board | `board_read`, `board_trace` | Read-only (Phase 17) |

### 2.2 Events (`emit` → main window)

Events go to the main window (`emit_to`), never a global broadcast. The turn loop talks to an
`EventSink` (`agent/event.rs`), never to an `AppHandle`; `WindowSink` is its subscriber. A later
messaging face (§ 7.7) is another sink, not a second turn loop.

| Event | Carries |
| --- | --- |
| `turn:started`, `turn:delta`, `turn:message`, `turn:finished`, `turn:error` | a turn's lifecycle: model, text deltas, the final message, stop reason and usage, errors |
| `tool:requested`, `tool:drafting`, `tool:approval_required`, `tool:approval_annotated`, `tool:approval_resolved`, `tool:started`, `tool:progress`, `tool:finished` | a call's lifecycle: redacted arguments, arguments still streaming, the approval request, the decision model's advisory annotation of it (§ 7.18), who resolved it, shell output chunks, outcome |
| `session:updated` | a session summary, for list badges without a refetch |
| `audit:appended` | a new audit line |
| `settings:changed`, `connector:updated`, `routine:updated` | store changes |
| `workspace:dropped` | files dropped on the window: a drop id, names and position (§ 7.15) |
| `tray:activate` | a tray action |

`seq` is a per-turn monotonic counter on deltas and progress; the UI drops out-of-order or duplicate
values. Every payload carries `session_id` where it has one, and no secret crosses the boundary:
settings are masked, the process environment is never sent, and content is truncated with an
explicit flag.

## 3. Tool policy matrix

`WS` is the canonical workspace root of the session's project. *Contained* means the resolved path —
links followed, `..` normalized — is `WS` or below it.

Two checks come before the table. A call for a tool the identity does not hold is `E_DENIED` with no
dialog: an allow-list narrows what an identity could ever do and never auto-allows. A call in a
session with no workspace is `E_NO_WORKSPACE`.

| Tool | Condition | Decision | Session grant | Risk |
| --- | --- | --- | --- | --- |
| `fs_list` | contained | **auto** | — | low |
| `fs_list` | outside | **ask** | no | medium |
| `fs_read` | a declared source of a world, unchanged since perceived (§ 7.2) | **deny** | — | — |
| `fs_read` | contained, sensitive name | **ask** | no | high |
| `fs_read` | contained, > 1 MB | **ask** | `FsReadLarge` | low |
| `fs_read` | contained, otherwise | **auto** | — | low |
| `fs_read` | outside | **ask** | no | high |
| `fs_write` | outside | **ask** | no | high |
| `fs_write` | under `world/`, delegated run | **deny** | — | — |
| `fs_write` | under `world/`, session | **ask** | `WorldAmend` (none when unattended) | high |
| `fs_write` | applies a skill proposal, session (§ 7.13) | **ask** | no | high |
| `fs_write` | applies a proposal from a brief, or one that does not parse, or onto an existing `SKILL.md` | **deny** | — | — |
| `fs_write` | applies an eval proposal, or writes an `eval.yml` directly, session (§ 7.18) | **ask** | no | high |
| `fs_write` | writes an `eval.yml` from a brief, or applies a proposal that does not parse or onto an existing `eval.yml` | **deny** | — | — |
| `fs_write` | any segment `.git` | **ask** | no | high |
| `fs_write` | contained, otherwise | **ask** | `FsWrite` | medium; high on a sensitive name |
| `shell_exec` | working directory outside | **ask** | no | high |
| `shell_exec` | `git`, and the line is not read-only (§ 3.1) | **ask** | no | high |
| `shell_exec` | working directory contained | **ask** | `Shell { program }` | high |
| `screen_capture` | primary display | **ask** | `ScreenCapture` | medium |
| `skill_run` | a skill the identity was granted | **auto** | — | — |
| `skill_return`, `handoff_return` | every artefact contained | **auto** | — | — |
| `memory_write` | a non-empty sentence | **ask** | `MemoryWrite` | medium |
| `memory_search` | — | **auto** | — | — |
| `handoff_delegate` | 1..`FAN_OUT_MAX` well-formed briefs, not from a delegated run | **ask** | `HandoffDelegate` | medium |
| `<connector>__<tool>` | the connector is running and offers the tool | **ask** | `Connector { tool }` | high |
| `jev_eval` | a signed `.aegis/evals/<name>/eval.yml`; inputs contained and declared | **ask** | `JevEval { name }`; none with a credential-shaped input | high |
| `jev_eval` | only a `PROPOSAL.yml`, no such eval, one that does not parse, an undeclared or outside input | **deny** | — | — |
| `jev_ask` | a non-empty state under 64 KiB, well-formed questions | **ask** | `JevAsk` | high |

Order inside a tool matters: hard denials first, then containment, then the specific rows. A new
tool is an ask by default (§ 7.2 row 7). In an unattended run every ask not covered by a held grant
becomes a refusal (Phase 16). The decision model (§ 7.18) is never consulted by this table: its
annotation arrives after an ask is raised and changes no row.

**Sensitive names** (case-insensitive, every segment *below* the workspace root): `.env*`, `*.pem`,
`*.key`, `*.p12`, `id_rsa*`, `id_ed25519*`, `.npmrc`, `.netrc`, `credentials`, `.aws`, `.ssh`,
`*.kdbx`. A match never blocks; it turns an auto-allow into an ask and raises the badge. The badge is
advisory and never a condition.

**Path resolution** (`policy/path.rs`) is the only place a model-supplied path is interpreted, and
tools receive resolved paths from the decision.

- Components are walked one at a time; a link is canonicalized on the spot, so `..` pops the
  resolved path, not the lexical one. A missing tail is kept as written.
- On Windows the existing part is canonicalized, so short names (`GIT~1`) and case match the disk.
- Comparison is component-wise, case-insensitive on Windows; verbatim and UNC prefixes compare by
  meaning. `C:\ws2` is not inside `C:\ws`.
- The lexical answer is kept beside the real one: an argument that *looks* contained and resolves
  outside is a link escape, which is a hard denial.
- The sensitive-name, `.git` and `world/` predicates read the path relative to `WS`.

### 3.1 Grant semantics

A session grant is created by answering `allow_session`. It is:

- **Narrow.** The key is a scope, never a tool as a whole, and `scope_label` states it in words on the
  request and in the grant list:

  | Grant | Key |
  | --- | --- |
  | `FsReadLarge` | contained reads over 1 MB |
  | `FsWrite` | the `WS` subtree, except `.git/` and `world/` |
  | `WorldAmend` | writes under `world/`; never matches the `FsWrite` rows, nor they it |
  | `Shell { program }` | a bare name: the program name (basename; on Windows without its executable suffix, lower case). A name with a separator: its **resolved absolute path** (lower case on Windows), so `scripts\git.cmd` is not `git` |
  | `ScreenCapture`, `MemoryWrite`, `HandoffDelegate` | that call type |
  | `Connector { tool }` | the full tool name, never the connector: a server may add tools mid-session |
  | `JevEval { name }` | one signed eval by name |
  | `JevAsk` | model-written questions to TypeSafe; signable on a routine |

- **Read-only for git.** A grant on `git` covers a line only when (a) the verb is one of `blame`,
  `cat-file`, `describe`, `diff`, `log`, `ls-files`, `ls-tree`, `rev-list`, `rev-parse`, `shortlog`,
  `show`, `status`, `version`, or `branch` with listing options only; (b) nothing precedes the verb
  but `--no-pager`, `-P`, `--no-optional-locks`, `--literal-pathspecs` or `--version`; (c) no
  argument is `--output`, `--no-index`, `--contents` or `--ext-diff`; and (d) no folder between the
  working directory and `WS` is laid out like a bare repository (a `HEAD` beside `objects/` or
  `commondir`, before any `.git`). Every other `git` line offers no grant. The previous deny-list of
  tree-moving verbs let `-c core.fsmonitor=…`, `git config` and aliases run under the grant.
  Detection uses the program name, so a path to a `git` binary follows the same rules.
- **Session-lifetime only.** In memory, keyed by session, dropped on close and exit. There is no
  "always allow".
- **Revocable.** `approval_grants` lists them, `approval_revoke_grant` withdraws one.
- **Only ever a collapsed ask.** The matrix names the grant a row would accept; a row offering none
  cannot be matched by anything in the store. That is how "never outside the workspace, never into
  `.git/`" holds without a second rule.

A routine's standing approvals are these same values, signed on the routine and seeded into its runs
(Phase 16).

### 3.2 Hard denials (no prompt)

Refused before any approval is offered, because approving them could not be meaningful:

- a path argument that is empty, relative but rooted (`\tmp`, `C:tmp`), or unresolvable (a dangling
  or looping link);
- on Windows, a path segment ending in `.` or a space, or containing `:` — Win32 would open another
  name (`.git.\hooks` opens `.git\hooks`), so a predicate reading the text would judge the wrong
  folder;
- a path that looks contained and resolves outside through a link;
- `fs_write` onto a directory or a non-regular file, or with a missing parent and no `create_dirs`;
- `shell_exec` with an empty program, this application's own binary, a working directory that is not
  a folder, or an execution host that cannot see it (`E_EXEC_HOST`);
- the **deny** rows of § 3; `handoff_delegate` from a delegated run; a skill the identity was not
  granted; a connector tool nothing answers to; a malformed brief;
- **at execution**, a resolved path (the `fs_*` target, the `shell_exec` working directory) that no
  longer resolves to itself — a folder became a link while the dialog was open. This narrows the race
  to two system calls; it is not a handle-based guarantee;
- a call arriving after `session_cancel` for its turn.

### 3.3 What this matrix is not

`shell_exec` takes `program` + `args` and uses no shell, so there is no metacharacter parsing to
defeat. A denylist of dangerous commands would be presentational: it may raise the badge, and must
never be described as a boundary.

The real boundary is narrow and stated plainly: the user reads the exact program, arguments and
working directory — plus the distribution, with an execution host (§ 7.12) — before anything
mutating runs. Tools run as the user; there is no sandbox. The `git` read-only grant is a scope, not
isolation: git still reads the user's own configuration. A later workspace-scoped executor (§ 7.9)
would limit where an approved command lands; it would not justify auto-allowing one.

## 4. Wire protocol

Two protocols, kept apart: one to the model over the network, one inside the runtime.

### 4.1 Runtime ↔ model

Providers sit behind one trait and normalize to one event stream; no provider JSON leaves
`agent/provider/`:

- `openai.rs` — OpenAI-compatible `POST {base_url}/chat/completions`, SSE, function calling, with
  `stream_options: { include_usage: true }` (streaming endpoints generally send usage only when
  asked);
- `motosan.rs` — Anthropic Messages (with cache breakpoints on tools, system and the newest message),
  ChatGPT Codex Responses and Gemini, through `motosan-ai`, including CLI logins (`oauth/`). The
  crate's CLI backends are off (`IDEAS.md` § 6);
- `fake.rs` — the scripted provider.

```jsonc
{
  "model": "<resolved binding: session, else identity, else the row's (§ 7.19)>",
  "stream": true,
  "messages": [
    { "role": "system", "content": "<identity, policy summary, workspace digest, world frame, memories, skill catalog>" },
    { "role": "user", "content": "..." },
    { "role": "assistant", "content": null,
      "tool_calls": [ { "id": "call_1", "type": "function",
        "function": { "name": "fs_read", "arguments": "{\"path\":\"src/main.rs\"}" } } ] },
    { "role": "tool", "tool_call_id": "call_1", "content": "<ToolResult envelope>" }
  ],
  "tools": [ /* schemas from the ToolSpec registry, filtered by the identity's allow-list */ ]
}
```

Tool schemas come from the registry; a tool is declared once and its schema, dispatch and policy row
key off the same name:

```
fs_list          { path, max_entries? <= 1000 }
fs_read          { path, offset?, limit? }                     // bytes
fs_write         { path, content, create_dirs? }
shell_exec       { program, args?, cwd?, timeout_ms? <= 120000 }
screen_capture   { display?: "primary" }
skill_run        { name }
skill_return     { report }
memory_write     { kind, text, source? }
memory_search    { query }
handoff_delegate { plan }                                      // briefs, optional reviewer
handoff_return   { report }
jev_eval         { name, inputs? }                             // paths; the eval file owns the questions
jev_ask          { state, questions[] }                        // offered only with a TypeSafe key
<connector>__<tool>  { … }                                     // the server's own schema
```

```rust
enum ModelEvent {
    TextDelta { text: String },
    ToolCallDelta { index: u32, id: Option<String>, name: Option<String>, args_delta: String },
    Finish { reason: StopReason, usage: Option<Usage> },
    Error { code: String, message: String, retryable: bool },
}
```

Tool-call fragments accumulate per `index`, and arguments are parsed only at
`Finish { reason: ToolCalls }`. A call whose arguments do not parse is not executed; it becomes a
tool message with an error envelope, so the model can correct itself.

### 4.2 Turn loop

```
session_send
  └─> Turn { id, session_id, cancel: CancellationToken }
      Building -> Streaming -> [ToolPending -> Awaiting -> Executing -> Building]* -> Done
```

1. **Building** — fold the transcript if it is over the compaction threshold (once, before the first
   request, so every round reasons over one history); build the request; emit `turn:started`.
2. **Streaming** — text deltas are coalesced into ~50 ms frames; `Finish` persists the message.
3. **ToolPending** — per call, `policy::decide`: `Auto` executes; `Ask` registers an approval, marks
   the session `awaiting_approval` and waits (five-minute expiry resolves as a denial); `Deny` skips
   execution with a denial envelope.
4. **Executing** — the tool's own timeout and byte caps, progress events, and exactly one audit line
   whatever the outcome.
5. One tool message per call, then back to Building.

Two guards, neither a permission gate: a **loop** (`E_TOOL_LOOP`) is the same round fingerprint
three times running; a **ceiling** of 64 rounds (`E_TOO_MANY_TOOL_ROUNDS`) bounds the bill when
work is still progressing. The same ceiling applies with or without a runbook. Hitting either
refuses the pending calls and gives the model one wrap-up round to finish; the recovery is not
"ask the user to continue" (§ 7.16). A skill run may still span turns of the same session, up to
four (`IDEAS.md` § 10).

### 4.3 ToolResult envelope

One shape for every tool, success or failure:

```jsonc
{
  "ok": true,
  "tool": "shell_exec",
  "content": "…",        // text, already truncated
  "truncated": true,
  "bytes": 131072,        // size before truncation
  "meta": { "exit_code": 0, "duration_ms": 812, "cwd": "…" },
  "error": null           // { "code": "E_DENIED", "message": "…" } when ok = false
}
```

Caps: `fs_read` 256 KB; `shell_exec` 64 KB of interleaved output (head and tail with an elision
marker) and a 120 s hard timeout; `fs_list` 1,000 entries; connector text 64 KB. `screen_capture`
never returns image bytes: it writes a PNG under the app data directory and returns
`{ path, width, height, sha256 }`.

A denial is an ordinary result (`ok: false`, `E_DENIED`); the turn continues.

### 4.4 Error codes

Stable strings, shared by IPC and envelopes: `E_TURN_BUSY`, `E_NO_WORKSPACE`,
`E_PATH_OUTSIDE_WORKSPACE`, `E_PATH_INVALID`, `E_DENIED`, `E_GRANT_NOT_ALLOWED`, `E_APPROVAL_STALE`,
`E_TIMEOUT`, `E_TOOL_FAILED`, `E_EXEC_HOST`, `E_PROVIDER_HTTP`, `E_PROVIDER_PARSE`, `E_NO_API_KEY`,
`E_KEYRING_UNAVAILABLE`, `E_CANCELLED`, `E_TOO_MANY_TOOL_ROUNDS`, `E_TOOL_LOOP`, `E_SCREEN_PERMISSION`,
`E_INVALID_SETTING`, `E_INTERNAL`.

`E_EXEC_HOST` is its own code because it says what no other does: the command ran nowhere, and the
project's host — not the call — has to change (§ 7.12).

## 5. Platform risks

User-facing symptoms and fixes are in `docs/troubleshooting.md`. These are the decisions.

### 5.1 Windows

- **WebView2** is a runtime dependency; the bundle uses the Evergreen bootstrapper.
- **Paths** carry most of the containment risk: verbatim `\\?\` prefixes, UNC shares, case
  folding, short names, and Win32 respelling of trailing dots and spaces. All handled in
  `policy/path.rs`, with tests (§ 3).
- **No shell.** Programs are spawned directly. `.cmd` / `.bat` shims (`pnpm`, `npx`) are resolved
  through `PATHEXT` and launched by `std::process::Command`, which since Rust 1.77.2 escapes arguments
  for `cmd.exe` itself; a hand-written `cmd /c` would not. This applies only when the host is this
  Windows process.
- **WSL is an execution host** (§ 7.12), not a compile footnote: `fs_*` over `\\wsl$\` is UNC, and
  running the Windows toolchain against a Linux project is not operating it.
- Children are spawned with `CREATE_NO_WINDOW`; Stop kills the tree (`taskkill /T /F`).
- **Captures**: per-monitor DPI; the dialog shows physical and logical sizes.
- **Credential Manager** holds ~2.5 KB per secret: enough for a key, not a token bundle.
- SmartScreen flags unsigned builds; the WebView2 `Chrome_WidgetWin_0` message on exit is Chromium's.

### 5.2 macOS

- **Screen Recording** consent appears on the first capture and is tied to the binary. A refusal
  looks like success (a blank frame), so a uniform capture is refused as `E_SCREEN_PERMISSION`.
- **Keychain** ACLs break on every dev rebuild; the environment key is the development default and
  Settings reports its source honestly.
- The tray is an `NSStatusItem` with a template icon. Closing the window hides it
  (`prevent_close`); quitting is explicit.
- WKWebView is strict on CSP and custom protocols: the CSP stays tight.

### 5.3 Linux (best-effort)

- **WebKitGTK 4.1**, not Chromium: plain CSS, no Blink-only effects.
- The DMA-BUF renderer blanks the window on some NVIDIA/Wayland setups; Aegis sets
  `WEBKIT_DISABLE_DMABUF_RENDERER=1` when unset (`display.rs`).
- The tray needs `libayatana-appindicator3` and is optional: the app stays usable without it and
  never panics over it. Under WSLg the tray is skipped.
- **Wayland blocks capture** by design; wlroots screencopy works, others fail with
  `E_SCREEN_PERMISSION`. Never a fake black frame.
- **Secret Service** is often absent; the environment key is the norm there.

### 5.4 Cross-cutting

- **Screenshots have the largest blast radius.** Never auto-allowed; no preview; path, SHA-256 and
  size in the audit, never the image; stored under app data, not the workspace; the dialog names the
  display.
- **No image bytes over IPC.** Captures are rendered through the `asset:` protocol, scoped at startup
  to the capture directory alone — and narrowed back after every file drop, which Tauri would
  otherwise add to the scope.
- **Backpressure.** Shell progress is coalesced and capped.
- **Capabilities stay least-privilege**: no `fs:`, `shell:`, `dialog:` or opener permission in
  `capabilities/main.json`. Every privileged operation is a policy-gated Rust command; a plugin
  permission there is a review flag.

## 6. MVP phases (landed)

One coding agent, files in sequence; each phase ended runnable. Conventional commits.

| Phase | Delivered | Exit |
| --- | --- | --- |
| 0 | skeleton, capabilities with no plugin grants | `pnpm tauri dev` opens a window |
| 1 | errors, state, tray, window lifecycle | the tray toggles the window; closing hides |
| 2 | persistence, projects | a picked workspace survives a restart |
| 3 | path policy, matrix, grants — before any tool | containment and the decision table tested |
| 4 | tool registry, fs tools, audit | fs tools driven through policy leave audit lines |
| 5 | sessions, scripted provider, streaming | tokens stream; cancel works |
| 6 | approval gate end to end | allow once / session / deny; denial does not end the turn |
| 7 | shell tool | runs under approval on all platforms; `.cmd` shims, timeout, truncation |
| 8 | real provider, secrets | keyring + env fallback, masked, `settings_probe_provider` |
| 9 | screen capture | Windows and macOS, TCC failure path, clean Wayland refusal |
| 10 | audit drawer, polish | the walkthrough passes on two platforms |

MVP "done when": `pnpm tauri dev` launches a window and tray, a workspace can be picked, a message
sent, a streamed reply seen, a tool call approved, and an audit line found on disk.

## 7. Horizon — Chef de Cabinet (`COS.md`)

The MVP was the first slice of a Chef-de-Cabinet harness, not one itself. Compatibility held because:

- the MVP stayed a single-loop, approval-gated runtime over one workspace per project;
- durable facts never became "whatever is still in the chat";
- tools, policy and audit stayed name-keyed and extendable;
- domain work arrives as **workspaces + skills + MCP servers**, not core modules;
- irreversible actions never auto-fire.

`COS.md` *Bar* is the acceptance test: without shared files, per-agent memory and a skill runner, a
CoS recites.

### 7.1 Seams the MVP kept open

Constraints that still hold, not work to do.

| Seam | Must not |
| --- | --- |
| **Provider** | key the turn loop on a global singleton that cannot become a roster |
| **Decision model** | treat a System One model as a chat `Provider`; let the LLM invent the questions as the primary path; dump the transcript or `world/` as state; or skip the gate because of a probability or a confidence (§ 7.18) |
| **Agent identity** | persist "the assistant" as the only identity, or keep a role prompt only in the transcript |
| **Transcript** | become the source of truth for decisions, briefs or status |
| **Workspace** | grow a second hidden agent-memory filesystem that bypasses the workspace and the matrix |
| **Tools** | special-case policy or the turn loop on built-in versus MCP |
| **Policy** | offer "always allow forever", or a mutating path that skips the gate |
| **Audit** | freeze the line schema (it grew `agent_id`, `skill`, `handoff`, `routine`) |
| **Process** | quit on last window close (it would kill the scheduler) |
| **Settings / keys** | put keys in the WebView, or freeze the settings payload against a provider list |
| **Project** | assume a project is a software repository. A finance or watch folder is a folder — versioned when its convention is laid down (§ 7.11), not therefore a codebase. Do not assume the UI host OS is the tool host OS (§ 7.12) |
| **System prompt** | grow into runbooks: recurring procedure belongs in a skill (§ 7.6) |
| **Control surface** | add a second agent loop for a messenger, store messenger ids in sessions, open an inbound webhook, or treat WhatsApp as a control face |
| **Remote bind** | bind `0.0.0.0`, use Tailscale Funnel, embed tsnet, or add an HTTP API with a different command set than § 2 |
| **Tool executor** | hard-wire `Command` / `std::fs` / `CreateProcess` so a workspace-scoped executor or an execution host cannot sit behind the same `ToolSpec`; treat a denylist or `allow_session` as isolation; give the agent the host desktop |

### 7.2 Mapping the CoS primitives onto this tree

| # | CoS primitive | Where it lives |
| --- | --- | --- |
| 1 | Agent registry (role, tools, skills) | `agents.json`, Phase 12 |
| 2 | Handoff bus with a fixed schema | `handoff/`, Phase 15 (`COS.md` *Handoff*) |
| 3 | Workspace as shared memory | the **cabinet** under `.aegis/` (Phase 11) and the **constitution** `world/` at the root. Ordinary files: no editor in the WebView (a read-only explorer is § 7.15), versioned by § 7.11, revealed by § 7.10 |
| 4 | Memory per agent | `memories.json`, Phase 14 |
| 5 | Skill runner (`SKILL.md`) | `skills/`, Phase 13, § 7.6 |
| 6 | Scheduler of routines | `schedule/`, Phase 16 |
| 7 | Approval policy | § 3 — new tools (send, deploy, post, trade) are new rows, default **ask** |
| 8 | Compactor | `compact.rs`, Phase 14: state, not a summary; the CoS compacts a board, never other agents' transcripts |
| 9 | Status board | `board/`, Phase 17: attention, in flight, blocked; silent when empty |
| 10 | Trace / replay of a run | the audit log with one id over the CoS and its specialists; `board/trace.rs`, Phase 17 |

How the machinery is used (`COS.md` *Work*):

**Scarcity.** Human methods optimise calendar time and scarce writing. For agents, generating an
instance is cheap and **re-perceiving** a project that already lives in `world/` is the waste; the
unit of cost is a round-trip.

**Cabinet and constitution.** The cabinet (`.aegis/briefs/`, `status/`, `artefacts/`, `decisions/`,
`skills/`, `evals/`) is in-flight work, rewritten every turn. `world/` holds what the thing *is*: essence,
perceived schema, behaviours (sins included), oracle, essence decisions, declared sources.
Specialists read it and do not write it. `.aegis/decisions/DECISIONS.md` is operational;
`world/decisions.md` is essence.

**A sin has a perimeter.** A behaviour recorded from a source names the contract, role or class of
tasks it binds. Promoting or deleting one amends the world. No agent of care, no decay clock, no
extractor mining transcripts.

**Several worlds, later, as files.** A world may declare `needs` and `offers` as files so another
consumes a form already paid for — a versioned contract, not a fusion, not a runtime marketplace, not
a phase. Theatre until two workspaces actually have an essence.

**Unit of work.** An **oracle clause** (a claim evidenced by artefact paths) or an **écart** (the brief
would change the essence). Not an activity ticket.

**The CoS compiles.** Given a world, emit an instance and verify it against the oracle as a program.
Regenerating is legal. Fan out when file surfaces do not collide.

**Who writes `world/`.** Specialists: no — a refusal, not an ask with a grant. An écart returns
`needs_you` with one sentence and `next_owner` the CoS; amending the world is a cabinet act by a
human. Policy is the permission system, not a checksum of `world/`.

**What is still hashed.** Declared sources (`world/sources.yml`). Only the operator replaces them;
that is the one legitimate re-perception, bounded to the delta. At a brief's launch, drift means the
brief does not go out unless it is the perceive-delta.

**Frame, not a skill.** The standing constraint — read `world/`, do not write it, do not reopen the
sources, stop on an écart — is injected by the harness, because a skill can be skipped. It carries
status, never `essence.md`. The absence of a world is a shorter frame of the same kind (§ 7.17):
the two layers and the runbook name, not a procedure.

**Library skills.** `world.draft`, `world.perceive-delta`, `world.verify` and `world.check` are seeded
like any runbook and granted like any runbook. There is no `world.amend` for specialists.

*As landed* (`world.rs`):

- A `world/` holding at least one of `essence.md`, `schema.md`, `behaviours.md`, `oracle.md`,
  `decisions.md` is a world; `sources.yml` alone is not. **Nothing scaffolds it** — no command and no
  button.
- It sits at the workspace root; the cabinet moved under `.aegis/` in the same change. Workspaces
  laid out before keep root directories, reported as strays and never moved.
- The frame is a `transcript::Context` field built per round beside the cabinet digest. Without a
  world it is the absence paragraph (§ 7.17). With one, its *write* paragraph depends on the run: a
  brief is told it does not write `world/`; a session is told a person asking *is* the decision and
  `world.draft` is the runbook. A single paragraph for both made a session decline even when asked,
  leaving no `fs_write` in the audit — a prompt refusing is much harder to find than a gate refusing.
- Two matrix rows, chosen by the **run**, not the identity: delegated → deny; session → high-risk ask
  with `Grant::WorldAmend`, which matches no `FsWrite` row. Unattended runs are offered no grant, and
  `schedule::check` refuses to store it on a routine.
- Only the first path segment counts (`src/world/` is untouched). `fs_read` of a declared source that
  still hashes as recorded is denied; a moved source falls through to the ordinary rows.
- Drift is measured where it changes a decision: `handoff::runner` compares hashes before a brief
  opens its session (refusing unless the brief's inputs name a drifted path); the frame reports only
  what is cheap to see; `world_status` does the expensive read for the panel.
- `world.draft` writes `schema.md` and `behaviours.md` from named evidence and asks the human for
  `essence.md` and `oracle.md`. Seeding is recorded per name in `skills/.seeded`. `cos.loop` gained
  step 0: source drift before routing.
- Not done, deliberately: `shell_exec` writing `world/` is covered only by the shell prompt, and a
  checksum of `world/` as an attention signal is not written.

### 7.3 Post-MVP phase order

Each phase ended runnable; none depended on a later one; domain work came last. The slices
§ 7.10–7.19 are not steps in this list and did not delay it.

**Phase 11 — Workspace convention.** Shared memory as files a session reads at start and writes
through the gate. Exit: a decision and a status filed without a new agent type.

- `workspace_scaffold` creates only what is missing; the digest carries `STATUS.md` and the end of
  `DECISIONS.md` (2 KB each) and file *names* for briefs and artefacts. Versioning is § 7.11.
- The five directories live under `.aegis/`: the cabinet is the harness's working surface, so it
  goes in the harness's directory; `world/` is the project and stays at the root. The dot is not a
  hidden store — same containment, gate, audit and commit.

**Phase 12 — Agent registry.** Identities as data; sessions bind to one; tools not granted are not
seen. Exit: a reviewer identity cannot see tools it was not granted.

- `Agent { id, name, role, instructions, provider_id, tools[], skills[], builtin }`. `agent_id` is
  fixed at session creation and never rebound.
- The default identity is a **constant in the runtime, not a row**: every older session resolves to
  it, and it cannot be deleted from under one. It holds every tool and no skills.
- The allow-list is enforced twice: `tools::schemas_for` filters what the model sees and
  `policy::decide_call` refuses an ungranted name before the matrix, with no dialog. The audit line
  carries `agent_id`. `provider_id` resolves through `AppState::provider_for`, where a roster lands.

**Phase 13 — Skill runner.** § 7.6. Exit: the catalog lists; a library skill and a workspace stub run
end to end; the body is absent from turns that did not run it. No `skill_create`, no editor.

**Phase 14 — Per-agent memory and compaction.** Exit: after a forced fold the agent still knows the
goal, the blockers and where the decisions are.

- `Memory { id, agent_id, kind, text, source, … }` with `kind` in `preference | exception |
  convention` — the whole vocabulary. Every accessor takes an `agent_id`; no tool argument names an
  identity.
- **No `memory_forget` tool.** The store has full CRUD, the model has create and read, and Forget is a
  button: a delete most often removes a human correction. `memory_write` is an ask with a session
  grant because a memory reaches every later turn. Search is a capped substring scan. Consolidation
  is at the door: a repeated sentence touches the existing record.
- Compaction is **coded, not summarized**: `compact::plan` derives state from what happened (first
  ask, paths written, programs run, skill statuses, open questions, refusals) — deterministic and
  checkable against the audit. The last `compact::KEEP_TURNS` turns stay raw. `Compaction {
  through_message_id, folded, state, at }` is a pointer; nothing is deleted, and a later fold
  re-derives from the messages. The cut is always before a `user` message. Automatic past
  `COMPACT_AT_BYTES`, once per turn; forced by `session_compact`. Memory and the digest are rebuilt
  into every request, so there is no retrieve-after-compact step.

**Phase 15 — Handoff bus and the Chef-de-Cabinet loop.** Exit: one brief fans out to two specialists
in parallel and the CoS returns a status, not a concatenated transcript.

- `handoff/` holds both halves of the object (`Brief`, `Report`), because `return_format` is a promise
  about the report and `next_owner` starts the next brief. `check_brief` enforces **inputs are paths,
  never paste**: a multi-line input is refused.
- `handoff_delegate` asks with a session grant covering the routing only; `handoff_return` is how a
  delegated run answers.
- A delegated run is **an ordinary session** under the owner's identity, driven by the ordinary
  `Turn`, visible with a `brief` badge. `Delegated { handoff_id, from_session_id, brief }` on the
  record says where it came from.
- `bus` is policy, `Runner` is machinery: one task per brief, joined in order; `ATTEMPT_TIMEOUT`
  through the turn's token; two attempts, the second in the same session; then `needs_you` naming the
  human. Fan-in is a reviewer brief handed artefact paths, never sessions.
- Depth is one, enforced in `decide_call` (`Standing::{Own, Delegated}`): a delegated run is not
  offered `handoff_delegate` and always has `handoff_return`.
- The audit line grows `handoff`: one id over the CoS and every specialist.
- The loop is **a skill, not prompt text**: `cos.loop`, seeded, granted separately.

**Phase 16 — Scheduler.** Routines fire a skill on a clock or trigger, with budgets, pause, "fire" and
"clone" a role. Exit: a watch routine runs with the window hidden, writes status, and pings only if
the skill says so.

- `schedule/mod.rs` is policy (which routine may exist, when one is due, what its run is told);
  `runner.rs` is machinery (tick, session, deadline, record).
- `Routine { name, project, agent, skill, schedule, grants[], runs_per_day, paused, armed_at, last }`
  has **no prompt field**: a routine is a runbook's name. `Schedule` is `Every { minutes }`,
  `DailyAt { hour, minute }` (local time) or `OnChange { dir }`, polled on the tick.
- **Phase 16's door**: a routine names a **live** skill (`SKILL.md`, never a `PROPOSAL.md`), already
  granted, already run under watch at least once — checked by `AuditLog::witnessed`, a
  `skill_return` by that identity for that skill. It is the one place the runtime reads its own log to
  decide something, and it is not enforced in the UI.
- A run is unattended as a policy fact: `PolicyCtx::unattended` turns every ask into a refusal, and
  what a run may do beyond reading is the `Grant` list signed on the routine, bounded at save time by
  the runbook's declared tools and the identity's allow-list. **Run now** takes the same path. A
  scheduled run does not delegate.
- The run is an ordinary session with a `routine` badge; the audit line grows `routine`.
- Budgets are persisted and charged under the store's lock before the session opens, per routine and
  per identity. Two silent runs in a row pause the routine; `blocked` is an answer. Runs are cut at 15
  minutes; at most two are in flight. Firing a role refuses while routines use it; cloning is
  *Duplicate*, which copies no memories.

**Phase 17 — Status board and trace/replay.** Exit: "who ran, what did it cost, why did it fail"
answered without opening a chat.

- `board/mod.rs` reads `STATUS.md` structurally (the three headings; indented examples and
  whole-line italics dropped, which is how an empty board stays silent) beside what the runtime
  knows, every line saying which. **Nothing writes**: correcting status is an `fs_write`.
- `board/trace.rs` folds runs from the log, never storing them. `RunRef::of` takes the widest id:
  `handoff`, then `routine` + session, then `skill` + session, then the session. A report wins over a
  refusal inside it; a conversation cannot fail; a brief, runbook or firing that never reported has
  failed unless still running. Replay is the audit lines themselves.
- **Tokens are not on the audit line**, the one departure from § 7.1's list: a turn that called no
  tool still spends. Cost is a `TurnCost` per finished turn on the session, joined on `turn_id`.
  Missing usage is recorded as unknown, and totals read *at least*. Every turn belongs to exactly one
  run. Running it found that streaming endpoints send usage only when asked, so
  `stream_options.include_usage` is now sent; a server refusing it fails loudly.

**Phase 18 — MCP client.** External servers register into the registry and inherit § 3. Exit: one
external server callable under the same dialog as `fs_write`.

- `mcp/client.rs` is one stdio connection; `mcp/mod.rs` the roster and catalog;
  `store/connectors.rs` the record; `tools/connector.rs` the envelope.
- `agent/turn.rs` gained a catalog snapshot per turn and no branch: `tools::schemas_for` appends the
  catalog's schemas. No `if connector` in policy, dispatch or audit.
- `ResolvedCall::Connector` carries the model's JSON and nothing more, because it cannot be resolved,
  so **the row always asks**. `readOnlyHint` is shown, attributed, and never acted on.
  `Grant::Connector` and the allow-list key on the full tool name (servers re-list tools mid-session).
- The handshake advertises no client capabilities: no `sampling` (a second agent loop with no
  identity or dialog), no `roots`, no `elicitation`; resources and prompts are not read. A server
  asking anyway gets `-32601`. The child gets `env_clear()`, the platform floor, and only the named
  variables.
- The built-in identity holds every connector tool, being "every tool this build has"; no other
  identity gains anything by an install.
- Tested against a real process: the test binary itself serves MCP. That found `npx` being a `.cmd`
  on Windows (resolved through `PATHEXT`, as `shell_exec` does).

**Phase 19 — Domain packs as skills, not runtime.** One pack at a time — a workspace, skills, the MCP
servers it needs and a specialist identity — each allowed to fail without blocking the next. Never
add a domain by growing `agent/turn.rs`.

1. **Client delivery** — repositories, deploy drafts, alert drafts. Destructive deploys stay gated.
2. **Client intake** — mail first: read and draft, never send.
3. **Watch** — scheduled research, artefacts in the watch workspace.
4. **Budget and portfolio** — read-only connectors, a status file, alerts. Not a broker.
5. **Social** — find posts worth answering; draft replies and posts. Publishing is irreversible.
6. **Revenue experiments and wish list** — goals and proposals as files. Money movement is always
   human.

*As landed*, each pack was three `SKILL.md` files, their `skills::SEEDED` entries and documentation —
no command, tool, matrix row, binding or UI change. What each settled:

- **Delivery.** Library scope: how you review is how *you* work; how an app ships is its
  `.aegis/skills/`, which `deploy.draft` reads first. Aegis ships no connector and no identity; the
  runbooks work with none (`the_delivery_pack_calls_only_tools_this_build_has`). Each runbook's last
  step is *stop*, because a plausible yes at the end of a procedure is how an irreversible act gets
  taken by momentum. Against the plausible deploy, a missing account of how the project ships is
  `blocked`; the incident note keeps observed and inferred apart.
- **Intake.** No runbook declares `shell_exec` — its inputs are written by strangers
  (`the_intake_pack_holds_no_tool_that_runs_a_command`), so Delivery and Intake are two identities.
  An ask is a quoted, dated sentence, so *no ask* is available; `thread.recap` counts quoted sentences
  once and separates agreed from outstanding; `reply.draft` names a file behind each commitment and
  needs a ticket path. Money or access requests always return `needs_you`. Attachments are named, not
  read (an `.eml` is mostly base64). A catalog line is cut at 160 characters, so *When to use it* opens
  short (`a_domain_pack_says_when_to_run_it_without_the_line_being_cut_off`).
- **Watch.** *Scheduled* is the property: `the_watch_pack_can_be_put_on_a_clock` runs `schedule::check`
  on all three. No command, because a signed `curl` fired at night is an outbound channel. Claim kept
  apart from evidence; bookkeeping by file names; a quiet period writes nothing and returns `done`.
  `watch.impact` writes conditions, not conclusions; an écart goes to a person, and a routine cannot
  sign `Grant::WorldAmend`.
- **Budget.** Arithmetic fails silently, so a figure is **copied** or **shown**, and stated totals are
  reconciled. No `shell_exec`: *not a broker*
  (`the_budget_pack_could_not_reach_a_broker_if_it_tried`). Positions dated by their stalest input;
  runway as a range; an alert ends with one question and no proposal; thresholds must predate the move.
- **Social.** The artefact is public and permanent, so both drafting runbooks end at
  `never-send-without-review` (`a_draft_somebody_else_sends_names_the_runbook_that_checks_it`). The
  adversary is engagement: the refused shapes are named, and being wrong on the internet is never an
  item. The criterion is read from a file before the export; `social.post` refuses the future tense
  (`the_social_pack_holds_nothing_that_could_publish`).
- **Revenue and wish list.** The material has not happened, so nothing takes the grammar of a fact:
  unordered, not priced, a dated falsifier or no thesis. Two prefixes keep goals and proposals apart:
  a thesis reads neither the wish list nor the position, and the pipeline links no proposal to a goal.
  A wrong thesis is appended to, never deleted. A goal is a file, not a memory
  (`a_goal_is_a_file_and_not_something_an_identity_remembers`).
- **The whole.** Six domains arrived as eighteen files, and `agent/turn.rs` was never opened. The
  catalog of the 24 seeded runbooks measured 5,556 characters against a bound of 7,424 derived from the
  per-line cap (`a_library_holding_every_pack_still_costs_a_bounded_block`).

### 7.4 Hard rules that survive every later phase

- Do not expose the runtime on the public internet. Remote access is the same process over a private
  network, or it does not exist.
- Send, pay, merge, publish, deploy, trade: human gate. A verifier (agent or CI) can raise confidence;
  it cannot flip the default to auto.
- The CoS may *see* state. It may not merge or send unless that identity was granted those tools.
- Two failures → human, not twelve creative retries.
- A messaging surface is not an agent.
- Trading, monetization and the wish list are **funding goals expressed as files**, never a broker or
  a poster in `src-tauri`.
- Files stay ordinary files. The WebView may list and preview them (§ 7.15); it does not grow an
  editor. A session writes a runbook the way it writes a decision: `fs_write`, under the gate. A laid
  down workspace is a git work tree (§ 7.11); a commit is a gated `shell_exec`.
- The UI host OS is not assumed to be the tool host OS (§ 7.12).
- Specialists read `world/` and do not write it. An écart escalates. Amending the constitution is a
  human decision.
- The unit of CoS work is an oracle clause or an écart. The CoS compiles and verifies as a program.
- Do not copy a human project-management method into a skill, a prompt or the board.
- Credentials, the provider roster, installed MCP programs and identity rows stay install-global.
  The cabinet — `.aegis/`, `world/`, workspace skills, a roster proposal, routines naming a project —
  is per-project. No `settings.json`, `agents.json` or key in the workspace. The allow-list living on
  the identity is a known seam (`IDEAS.md` § 13).

### 7.5 What would make the mode unusable

- Building the CoS graph before workspace files, memory and skills.
- One context window holding the whole codebase, life and chat history, called orchestration.
- One generalist with every connector loaded instead of specialists.
- Auto-sending, auto-posting, auto-trading or auto-deploying to finish a demo.
- A second runtime or agent loop for a messenger, a phone inbox or Tailscale; an inbound webhook;
  embedding Tailscale, enabling Funnel or binding `0.0.0.0`.
- A fleet orchestrator or hypervisor control plane in `src-tauri` (§ 7.8, § 7.9); giving the agent the
  host desktop.
- Compaction as an LLM summary instead of coded state.
- Domain excitement (a broker API, a WhatsApp bridge) jumping ahead of the primitives.
- Dumping a procedure into a system prompt or a chat, then scheduling it. Until the runbook file
  exists, the work stays manual.
- An in-app editor or save path from the WebView; listing `node_modules/` as the default tree.
- A `skill_create` command, a WebView write into the library, or a session granting itself a skill
  it wrote.
- A first-run wizard, seeded identity rows, or an `agent_create` tool. Founding is a proposal, then
  apply (§ 7.14).
- A `settings.json` or `agents.json` under `.aegis/`. Conflicting grants across cabinets are a binding
  (`IDEAS.md` § 13), not a second settings file.
- Inserting a slice (§ 7.10–7.19) into § 7.3 as a fractional phase, or delaying a phase for one.
- Teaching the model to call `wsl.exe` or `bash -c`; falling back to Windows when WSL is missing.
- `git init` on `project_create`, a nested repository, auto-committing writes, or a GitHub product in
  the runtime.
- Running the CoS as Scrum; a specialist exploring a repository whose world is already in `world/`,
  or reopening a declared dump.
- Hashing `world/` as the permission system; a `world.amend` skill on every identity; the world novel
  in every prompt; empty `world/` templates in a workspace with no essence.
- Cherishing the instance instead of the oracle.
- An external memory engine (embeddings, a knowledge graph, a universal bank); auto-healing memory
  (decay, lessons mined from transcripts, a care pass writing `world/`).
- A runtime marketplace coupling projects.

### 7.6 Skills — why this is the efficiency layer

A skill is a **frozen how**. Without skills every specialist re-derives "how we triage mail" in its
context window; with them, the CoS says `run skill:inbox.triage`, the specialist loads the runbook
for that turn, and returns a strict status. It is also the only honest path to automation: a
scheduler fires a skill, never a vibe.

**Not a skill.** A tool is a verb on the machine; a memory is a preference or exception; an agent is a
perimeter and an allow-list. A skill *sequences* tools toward a done criterion, under that allow-list.
A new channel is a connector plus a skill, not code in `turn.rs`.

| Scope | Lives | Example |
| --- | --- | --- |
| Library | `skills/` in application data | `never-send-without-review`, `world.perceive-delta` |
| Workspace | `.aegis/skills/` in the project | how this app is deployed |
| Identity | the skill allow-list | which of the above it may run |

Headings are `COS.md` *Skills*; the runner enforces them.

- **Catalog in, body on demand.** Every request carries a short catalog line per granted skill; the
  body is loaded into the turn that runs it. Stuffing bodies into prompts is the anti-pattern.
- **CoS names, specialist executes.** A brief's `inputs` are paths; its `definition_of_done` can be a
  skill's return format. Fan-in is cheap because every skill returns the same object.
- **Verifier is a skill**, not a taste judgment: check the artefact against the definition of done.
- **Audit names the skill.** Every line of a run carries `skill`, or the run cannot be budgeted or
  replayed. Phase 17 depends on it.
- **No extra rights.** A runbook declaring a tool the identity lacks fails closed at `skill_run`.
- **Budgets.** A run may span up to four turns of a session, and a turn following a runbook may use 24
  rounds instead of 8 (§ 4.2).

**Authoring.** A skill is a file, so writing one is a file write — in the operator's editor (then
**Re-read**; the catalog is never cached), or through `fs_write` to `.aegis/skills/<name>/SKILL.md`
under the gate, where the preview is the moment a human signs the seven headings. The third path is
§ 7.13's proposal. The library is outside the workspace: a session writing there is the outside row
(ask every time, no grant).

**Writing is not granting.** `skill_run` requires the name on the identity's allow-list, edited in
Settings and in force on the next turn. A session cannot call `agent_update`. The built-in Assistant
can draft a runbook and cannot run one. A file that does not parse is listed with the reason and
never offered.

### 7.7 Messaging faces (control channel) — not scheduled

A face is a UI onto the existing loop, not a CoS primitive and not a domain pack. When scheduled it
lives at `src-tauri/src/channels/`, not a crate split and not a second runtime. `CONTROL.md` has the
shape: a transport-shaped `ControlChannel` trait, Keybase first (the logged-in CLI, E2EE, outbound
only), then X Chat, Telegram and Discord.

- Control verbs (`status`, `approve <id>`, `deny <id>`, `halt`) reach `approval_resolve` or cancel
  before any model sees them; free text is a turn. The matrix, approval expiry and audit get no
  bypass.
- Listening is outbound only: a local CLI child, long-poll, a gateway socket or an activity stream.
  A face needing an inbound listener (WhatsApp Cloud API, Telegram `setWebhook`, X webhooks, a tunnel)
  contradicts `AGENTS.md`.
- Approval detail is redacted on any face that is not E2EE.
- No provider switching over chat (that is the roster), no `shell:allow-spawn`, never speaking as the
  user on a public team or personal account. WhatsApp is not a control face.

### 7.8 Remote access (Tailscale) — not scheduled

Inbound (you reach this process) and outbound (this process reaches another machine) are different
things.

| Inbound layer | Exposed | Provided by |
| --- | --- | --- |
| **0 — host (preferred)** | nothing: you drive the real window over OS remote desktop, RDP/VNC or Tailscale SSH | the operator's tailnet |
| **1 — loopback (later, optional)** | HTTP + WebSocket on `127.0.0.1` only, the same commands and events as § 2, the same `EventSink` | the operator's Tailscale Serve or an SSH tunnel. Never Funnel, never `0.0.0.0`, never tsnet in this repo |

Native work (the folder dialog, capture of this machine, keyring prompts) still runs on the host.

**Outbound** is not remote access. There is no agent-to-agent wire: specialists are identities in one
process. Another machine or a VM is a **tool target** — `shell_exec` of `ssh`, `docker` or `sbx` under
a high-risk ask, or an MCP server that happens to live there. A remote model is a provider in this
process, or a CLI run under `shell_exec` whose payload is a brief, never a transcript. A mesh of Aegis
processes would be a second runtime: do not build it.

### 7.9 Tool containment — not scheduled

| Ask | Verdict |
| --- | --- |
| Orchestrate a fleet of agent processes | **Do not build.** Multi-agent is the in-process CoS; other machines are tool targets |
| Control VMs as a harness feature | **Do not build.** `docker` / `sbx` / Hyper-V on PATH already run under § 3 |
| Run *our* `fs_*` / `shell_exec` in a workspace-scoped box | **Later seam**, optional: containment for this process's tools, same `ToolSpec`, same gate |

The approval gate decides **who** may run a tool, not **where** its bytes land: an approved command can
reach the rest of the account. If a box comes, the split is:

| Stays on the host | May later run in a box |
| --- | --- |
| tray, WebView, policy, approvals, audit, keyring, `screen_capture` | `fs_*` and `shell_exec` against the workspace |

The box mounts only the workspace — not `$HOME`, `.ssh`, the Docker socket or the keyring — and API
keys stay on the host. Strength matters: a shared-kernel container is convenience; a microVM or
Hyper-V-isolated VM is isolation, on Windows too. The human gate stays inside the box, and "it is
sandboxed" never justifies auto-allowing a mutation. WSL is not this box: it is the operator's Linux
userland (§ 7.12).

### 7.12 Execution host (WSL) — landed

The UI host and the tool host differ for a Windows operator whose projects live in a WSL distribution
(`exec_host.rs`). Not a second Aegis, not a microVM (§ 7.9), not outbound SSH (§ 7.8).

- **Default: none.** `shell_exec` spawns on this process. Only Windows offers WSL; another OS refuses a
  recorded WSL host rather than ignoring it.
- `Project.exec_host: { kind: "wsl", distro } | null`, absent on old rows. Sessions, routines and
  delegated runs inherit it and cannot override it. Commands: `project_set_exec_host`,
  `project_list_exec_hosts` (`wsl.exe -l -q`, whose output is UTF-16LE).
- The `shell_exec` schema is unchanged; the model never passes `wsl` or a distro. The runtime spawns
  `wsl.exe -d <distro> --cd <linux cwd> --exec <program> <args>` — `--exec` keeps the vector with no
  login shell. The distro's PATH, HOME and user; never `-u root`. `PATHEXT`, `.cmd` shims and
  `CREATE_NO_WINDOW` apply only on the Windows host.
- The dialog names the distribution and the Linux working directory. The grant keys on the program,
  never on `wsl.exe`.
- `fs_*` is unchanged: containment is the Windows-canonical workspace; `\\wsl$\` is UNC.
- **Never**: `wsl.exe` as a model tool; `sh -c` around a model string; flipping the host from a
  `\\wsl$\` path (the picker may *mark* the distribution — `distro_of`, derived on read — because a
  label is not a decision, and `C:\…` projects built in WSL would not be caught anyway); Aegis under
  WSLg as the way to operate Linux projects; a second loop in the distribution; silent fallback to
  Windows.

*As built*:

- **Translation is a string rule**, not a `wslpath` round trip: `\\wsl$\<distro>\…` and
  `\\wsl.localhost\<distro>\…` lose the share, `C:\…` becomes `/mnt/c/…`. A UNC path naming another
  distribution is refused.
- **The probe is not optional.** `wsl.exe --cd` silently starts in `/` when it cannot find the
  directory (measured), so every hosted call first runs `wsl -d <distro> --exec test -d <cwd>`
  (~160 ms warm): exit 0 runs, 1 is "not a folder there", anything else is "not a distribution a
  command can run in" (`E_EXEC_HOST`).
- **`--cd` and no `current_dir`**: one answer to "where", the one the dialog showed.
- **Stop reaches the Linux process**: ending the `wsl.exe` relay ends the session it opened (measured
  with `pgrep`); the Windows tree kill covers it.

### 7.14 Cabinet founding — landed

### 7.16 Turn guards — landed

The round cap counted rounds as if a `review.diff` of forty calls and `fs_read` of the same file
forever were the same thing. Eight was never measured (`IDEAS.md` § 11). The turn then ended and
told the model to ask the user to continue — which is a human in the hottest path, and a silence
when nobody is there.

**In scope**: stop a stuck model; let progressing work finish in the same turn; still bound the
bill.
**Out**: a model that auto-approves or that judges "this is still progress" (`IDEAS.md` § 12);
removing a ceiling; synthesizing a user "continue" as a new turn.

*As landed*:

- **A loop is a fingerprint.** The round's identity is the tool names and canonical arguments,
  sorted, so parallel order and fresh call ids are not progress. Three identical rounds in a row
  refuse the third (`E_TOOL_LOOP`). Two can be a retry after a failed read.
- **A ceiling is a bill bound.** 64 rounds, the same with or without a runbook. Past it:
  `E_TOO_MANY_TOOL_ROUNDS`. Ordinary work should not hit it; a measured `review.diff` needed about
  twenty.
- **A halt wraps up.** The pending calls are refused, then the model gets one more request to
  summarize or `skill_return`. A second tool round after that stops. The envelope does not say
  "ask the user to continue".
- **Carry still exists.** Stop, a new user message, or a run past four turns still split a skill
  run across turns. The halt itself is no longer that split.
- **Unattended** is still bounded by the scheduler's `RUN_TIMEOUT` (15 minutes). The ceiling is not
  a second clock.

### 7.18 Decision models (TypeSafe / Jev) — landed

Jev (TypeSafe AI) is a System One model: typed questions against a state, values and probabilities
out. It does not generate text, tool calls or explanations, and it does not choose the next
action. Treating it as the turn-loop chat model is a category error. Treating it as a tool the
LLM uses to invent questions is the architecture TypeSafe designed against
([How to build with TypeSafe](https://docs.typesafe.ai/concepts/how-to-build-with-system-one)):
code owns the workflow; System One is inserted only where a snap judgment over unstructured data
is needed; answers are composed in code.

**In scope**: a first-class decision client beside the chat provider; a credential of its own; one
harness-owned eval whose questions live in Rust; project evals as cabinet files, collected then
signed like a skill proposal; a probe in Settings; `jev_ask` as a soupape, not the north star.
**Out**: wrapping Jev as OpenAI `chat/completions`; using it as `provider_id`; a gate that
auto-allows or denies from a probability; mining transcripts for questions; a composition language
that can send, pay or trade; growing `agent/turn.rs` with Jev-specific or domain-specific branches;
shipping TypeSafe as an MCP connector instead of first-class; putting the key in the WebView.

*Settles*:

- **Not a `Provider`.** `Provider::stream` produces `ModelEvent`s (text deltas, tool-call deltas).
  Jev produces none of those. It does not implement the trait, does not appear in
  `AppState::provider_for`, and never answers a turn. The chat provider and the decision client
  coexist: a session still needs an LLM.
- **Code owns the questions.** An eval is a frozen set of atomic questions, a state builder, and a
  composition function, in Rust, in one module. TypeSafe's own agent skill says agents are bad at
  writing questions; constants (questions and thresholds) stay in one place so a person can review
  them. Control flow, deterministic rules and side effects stay in code. Questions in one request
  are independent and run in parallel: ask every question the composition might need, including
  speculative ones, then ignore the rest in code. A second HTTP round trip is the exception, and
  only when the next state cannot be built without the first answer.
- **State is structured.** Prefer a JSON object with named fields; a string is for a single
  passage. Questions name the part they judge with a backticked path
  (`` `ticket.messages[0].text` ``). Do not dump the transcript, the system prompt or `world/`
  wholesale. Do not stringify an object into a blob on the way to TypeSafe: the structure is the
  context. Cap the payload (64 KiB). TypeSafe's request budget is about 32,000 tokens shared by
  state and questions; do not cap harness evals at a small question count.
- **Instructions and criteria may be structured.** A string is fine when the question is
  unambiguous. When options need contrast, use objects (`what`, `not_for`, `examples`) so the
  boundary is reviewable. The client accepts string | object | array for `instructions` and for
  each criterion, matching the HTTP API.
- **Compose in code, route on uncertainty.** Choice returns `choice` + `probabilities` +
  `confidence`. Score returns a position on the levels (it can land between them) + the same.
  Noul returns only `noul` (0..1): that probability *is* the uncertainty; there is no separate
  `confidence`. Thresholds sit next to the questions. High confidence never skips PLAN 3: send,
  pay, merge, publish, deploy, trade stay behind the human gate. A probability can only make the
  harness *more* cautious or more informative, not less gated.
- **A second credential, not an `AuthKind`.** `AuthKind` picks how the *chat* provider authenticates.
  Jev is a different key to a different host. Keyring account `typesafe-api-key` (service still
  `Aegis`); environment `AEGIS_TYPESAFE_API_KEY`; the chat key (`provider-api-key` /
  `AEGIS_API_KEY`) is never sent to TypeSafe. `settings.json` grows a nested `decision` object
  (`model`, optional `base_url`, `annotate_approvals`); schema version stays 1 with
  `#[serde(default)]`. Empty model means `jev-latest`. Empty base URL means
  `https://api.typesafe.ai`. `annotate_approvals` defaults to true: a key you saved is used for
  harness evals; the toggle turns that off without deleting the key. The WebView sees only a
  `MaskedDecision` (source, hint, model, base URL, the toggle) nested on `MaskedSettings` —
  PLAN 7.1's "do not freeze the settings payload against a provider list".
- **Client.** `agent/decision/`: HTTP `POST {base}/v1/systemone`, `Authorization: Bearer`. No
  TypeSafe JSON leaves that module. Reuses the process `reqwest::Client`. Default model
  `jev-latest`. A missing key or missing TLS client fails closed for harness evals (the dialog
  is unchanged) and is an envelope (`E_NO_API_KEY` / `E_PROVIDER_HTTP`) for `jev_ask`.
- **First consumer: a harness-owned eval, `tool_risk`.** When policy has already decided **ask**
  (a dialog is about to open), and a TypeSafe key is configured, and `annotate_approvals` is on,
  the runtime evaluates the call as the dialog already describes it. It does not change
  Auto / Ask / Deny. Unattended refusals do not call it. Latency is TypeSafe's (tens to hundreds
  of milliseconds); start it when the ask is emitted, show the dialog without the annotation if
  the eval is late or fails.

  State (object, no transcript): `tool`, `summary`, `reason`, `risk`, and the same preview the
  dialog shows (write preview already capped at 4 KiB). Questions, frozen here:

  | id | type | What it asks |
  | --- | --- | --- |
  | `destructive` | noul | Does this destroy data, overwrite a file, or run a program that can change the machine? |
  | `exfil` | noul | Does this send local file contents, credentials, or workspace text to a network service? |
  | `git_history` | noul | Does this change git history or repository state (commit, push, reset, rewrite)? |
  | `bucket` | choice | What kind of change: `workspace_write`, `shell`, `capture`, `outbound`, `read` |
  | `undo` | score | How hard to undo: revert the file / revert with git / likely gone |

  Composition (Rust, next to those questions): raise the wording on the dialog when `destructive`
  or `exfil` is high, or `undo` is toward "gone"; omit `bucket` when its `confidence` is low; never
  map an answer onto Auto. The annotation is advisory. PLAN 3 still decides.
- **Project evals live in the cabinet.** Recurring judgments of *this* workspace — classify a mail,
  does this invoice match the named envelope, does this thesis still hold given these files — are
  files under `.aegis/evals/`, not chat, not `world/`, not `agent/turn.rs`. `.aegis/decisions/` is
  the log of decisions *taken*; an eval is *how this project will judge* the next one. Essence
  ("we never trade") stays in `world/decisions.md` and is a human amend. A domain pack may *ship*
  example evals the way it ships runbooks; it still does not grow the turn loop (Phase 19).

  **Not a skill.** A skill sequences tools toward a done criterion (`COS.md` *Skills*). An eval is
  one System One request plus a bounded composition. A skill may name an eval as a step
  (`inbox.triage` runs `inbox.classify`, then files). An eval is not a seven-heading runbook, and
  a runbook is not a place to hide a free-form `jev_ask`.

  **Collect, then sign — the § 7.13 analogue.** TypeSafe's own skill says agents are bad at writing
  questions; the CoS may *notice* a judgment repeating in briefs and draft
  `.aegis/evals/<name>/PROPOSAL.yml` through the ordinary `fs_write` dialog. Nothing mines
  transcripts (`COS.md`: no extractor). Only `eval.yml` is runnable. Apply is a second `fs_write`
  copying the proposal byte-for-byte onto `eval.yml`; the preview is where the human signs the
  questions and the thresholds. No auto-apply, the CoS does not apply, an apply does not grant
  the identity, a routine cannot name a proposal. An existing `eval.yml` is not replaced by this
  path (hand-edit, or a new name). Unattended apply is refused. The listing of proposals is its
  own command, never merged into the grantable catalog.

  **File shape** (one document, reviewable): `name`; `when` (one line, for the catalog); `inputs`
  (paths the harness reads into a structured `state` object — a brief's rule: paths, never paste);
  `questions` (the TypeSafe map, atomic, structured criteria welcome); `compose` (the closed
  vocabulary below). A file that does not parse is listed with the reason and never offered.

  **Compose is a closed vocabulary**, interpreted in Rust, next to the questions in that file:

  | Form | Meaning |
  | --- | --- |
  | `noul <id> >= <t>` | the probability itself |
  | `choice <id>` | the selected option, only if `confidence >= <t>` (else uncertain) |
  | `score <id> >= <t>` | position on the levels, same confidence floor |
  | `weight` of nouls | a named sum with coefficients in the file |
  | `if … then escalate` | `needs_you` / `blocked`, one sentence |
  | `if … then route <label>` | a label for the caller (a skill, the board), not an action |

  No shell, no HTTP beyond the one TypeSafe call, no `fs_write` from the composer. Route labels
  are data. Send, pay, merge, publish, deploy, trade are still PLAN 3 — a `route: take_position`
  is a recommendation in the envelope, not a broker call. Budget arithmetic stays copied or shown
  in code; Jev judges the unstructured part (does this text match the envelope), it does not add
  the numbers. Trading evals *propose*; they do not execute (`AGENTS.md`).

  **Run.** Tool `jev_eval` `{ name, inputs? }`. The harness loads the signed `eval.yml`, resolves
  contained input paths, builds the JSON state, calls Jev, composes, returns the composed object
  (routes, escalations, the raw answers). The model does not supply questions. Extra `inputs`
  override paths declared in the file, still contained; they cannot inject a question. Policy:
  **ask**, grant `JevEval { name }` (narrow, like `Connector { tool }`), risk **high** — named
  workspace files leave the machine. Unattended without that grant refuses. A missing TypeSafe
  key is an envelope after approval.
- **Soupape: the tool `jev_ask`.** For a judgment the harness does not yet own — the draft that
  may become a `PROPOSAL.yml`, not the steady state. The model supplies structured state and
  atomic questions; the runtime does not dump the transcript. Granted per
  identity. The built-in Assistant holds it because it holds `tools::names()`; a stored identity
  does not gain it until the operator ticks it. The tool description states TypeSafe's rules:
  one snap judgment per question, many questions in one call, structured state, compose the
  numbers in the next step — do not ask Jev "what should I do".
- **Policy for `jev_ask`.** Every call **asks**. Session grant `JevAsk`. Risk **high**: arbitrary
  state leaves the machine, like a connector. Unattended without a held grant refuses through the
  existing last-check. Unlike `WorldAmend`, `JevAsk` *may* be signed on a routine. A missing key
  is a tool envelope after approval, not a policy denial. `schedule::check` does not special-case
  it. `compact.rs` needs no arm.
- **Probe.** `settings_probe_decision`: one cheap `noul` against a fixed probe state. Reuse
  `ProviderProbe`. Distinguishes no key, unreachable, 401, 422, 429/529, 200.
- **Commands** (update § 2.1 when this lands): `settings_set_decision` (`model`, `base_url`,
  `annotate_approvals`, `api_key?`), `settings_clear_decision_key`, `settings_probe_decision`;
  `eval_list`, `eval_proposals` (proposals never merged into the identity catalog). Do not
  overload `settings_set`. `ApprovalRequest` grows an optional annotation from `tool_risk`

  | --- | --- | --- | --- | --- |

  ```

  ```

  `tool_risk` is not a tool and has no matrix row.

*Refuses*:

- An `AuthKind::TypeSafe` in the chat Authentication dropdown.
- Letting the LLM invent the question set as the primary integration. `jev_ask` exists to *draft*;
  a live eval is a signed file. A proposal in the grantable catalog, or a CoS that applies, is

*`jev_ask` schema* (what the model fills; converted to TypeSafe's `questions` map inside
`agent/decision/`):

```
state: string | object | array        // required; cap 64 KiB of JSON. Keep structure.
questions: [                          // 1..; cap is the payload, not 32 items
  { id, type: "noul" | "choice" | "score",
    instructions,                     // string | object | array
    yes?, no?,                        // noul criteria (optional; string | object)
    options?: { name: description },  // choice, required, >= 2; description may be object
    levels?: [string | object, ...] } // score, required, >= 2
]
```

`id` is the key the answer comes back under. It is not sent to Jev as inference input. Duplicate
ids are refused at parse. `choice` / `score` missing their criteria are refused at parse.

### 7.19 Provider roster — landed

Phase 8 stored one chat provider. Phase 12 put `provider_id` on the identity and resolved it
through `AppState::provider_for`, "where a roster lands". Today the only accepted id is
`"default"`, Settings holds one row, one keyring account, and the model badge reads that
singleton. A CoS on one model and a specialist on another cannot be expressed (`IDEAS.md` § 9).
The trait and the turn loop still do not move.

Land this before § 7.18: Jev's settings trap is a second nested object on the same document, and
`inspect_account` is the secret helper it reuses. A new `AuthKind` remains a Settings row, not
this slice.

**In scope**: several named chat providers on this machine; a default `(provider_id, model)` on
each identity; a per-session override of that pair that does not rebind the identity.
**Out**: per-project providers (`IDEAS.md` § 13); a provider in `.aegis/` or in a roster
proposal; switching over chat (`CONTROL.md`); treating Jev as a `provider_id` (§ 7.18); a
second turn loop; rebinding `agent_id`.

*Settles*:

- **A roster is a list of rows, not a new trait.** Each row is `{ id, label, auth_kind, base_url,
  model, max_output_tokens }`. `id` `"default"` is reserved and cannot be deleted — it is the
  migrated singleton, and the built-in Assistant stays bound to it. New ids are UUID v4, minted
  on add, never typed. Label is display (empty allowed, 48 characters). Cap 16. Two rows may
  share an `AuthKind` (OpenAI and a local server are both `api_key`). The `Provider` trait, the
  dialects in `agent/provider/`, and `turn.rs` do not grow a per-provider branch.
- **One document, version still 1.** `settings.json` becomes `{ version: 1, providers: [...] }`.
  A document that still has the singleton `provider` object loads as one row `id: "default"` and
  is rewritten in the new shape on the next save. `#[serde(default)]` for anything nested later
  (`decision` in § 7.18). **Trap:** `SettingsStore` today locks and writes only `provider`. Lock
  and persist the whole file; a save of one row that does not round-trip the others (or a later
  `decision` object) drops them.
- **Keys are per row.** Service still `Aegis`. Account `provider-api-key` stays the default row
  (existing installs keep their key). Every other row is `provider-api-key:{id}`. Add
  `SecretStore::inspect_account` / `store_account` / `clear_account`; keep `inspect` / `store` /
  `clear` as wrappers on the default account so the refactor can land in pieces. `AEGIS_API_KEY`
  fills only the default row, and only when that row is `api_key` or `gemini` — never a second
  env var per id, never a CLI row. CLI logins (`claude_cli`, `codex_cli`, `grok_cli`) stay the
  CLI's own file; two Claude rows share that login and differ by model. `clear_key` on a CLI row
  is `E_INVALID_SETTING`: the key is not Aegis's. The WebView still never sees a key.
- **Binding, not a snapshot.** Identity grows `model` (empty string, `#[serde(default)]`: use the
  row's model). `provider_id` other than `"default"` becomes legal when that id is on file.
  `agents.json` version stays 1. The built-in Assistant cannot be edited: it keeps `"default"`
  and an empty model, so it tracks the default row the way today's singleton works. A cabinet
  proposal does not name a provider; `roster_apply` still writes `"default"` and an empty model.
  An identity edit reaches sessions that have not overridden, on their next turn — the same
  rule as instructions.
- **Resolve at the turn, one function.** `AppState::provider_for` takes the identity and the
  session. Effective `provider_id`: session override, else identity, else `"default"`. Effective
  model: session override, else (when the session overrode the provider) the row's model, else
  the identity's model if non-empty, else the row's model. A missing row on a hand-edited file
  warns and answers from `"default"`, as today; create, update and the session picker refuse an
  unknown id so that path stays a hand-edit. An unconfigured row is the scripted provider, as
  today. Handoffs and routines call the same function; they do not pick a model of their own.
- **Override is not rebinding.** `agent_id` stays fixed at creation (Phase 12). The session
  stores optional `provider_id` and `model` (`#[serde(default)]`, `sessions.json` version stays
  1). Absent means inherit. A model with no `provider_id` is "this identity's provider, that
  model". A `provider_id` with no model is "that row's default model". Both is the pair.
  `session_create` takes optional `provider_id` and `model`; omitted inherit. `session_set_binding`
  writes or clears the override; refused while a turn runs (`E_TURN_BUSY`), takes effect on the
  next send. Clearing both fields returns to the identity default. Delegated and scheduled
  sessions are ordinary sessions: created inheriting, overridable in the UI afterwards. Routines
  do not gain a provider field.
- **Delete is like `agent_delete`.** Refused for `"default"`. Refused when any identity or any
  session override names the row, with the counts, never cascaded, never a silent fallback that
  would change who answers. Removing the key is `settings_clear_key`, not delete.
- **IPC.** `settings_get` returns a list. Do not keep the flat `MaskedSettings` fields as a
  shadow of the default row — that is the freeze § 7.1 forbids.

  | Command | Role |
  | --- | --- |
  | `settings_get` | `MaskedSettings { providers: MaskedProvider[], keyring_available, presets }` |
  | `settings_set` | update one row (`provider_id` defaults to `"default"`; unknown id refused). Same fields as today plus `label?` |
  | `settings_add_provider` | mint a UUID, append a row, optional key |
  | `settings_delete_provider` | the rule above |
  | `settings_clear_key` | `provider_id` defaults to `"default"` |
  | `settings_probe_provider` | `provider_id` defaults to `"default"` |
  | `settings_list_models` | unchanged: `auth_kind` + `base_url`, for a form that is not saved yet |
  | `session_create` | optional `provider_id`, `model` |
  | `session_set_binding` | `session_id`, `provider_id?`, `model?` — both omitted clears |
  | `agent_create` / `agent_update` | `provider_id` must name a row; `model` may be empty |

  `settings:changed` carries the new `MaskedSettings`. `session:updated` after a binding change.
  `src/ipc/bindings.ts` is generated (`cargo test`); do not hand-edit. Update § 2.1 and § 4.1

  decision commands.
- **UI.** Settings is a list of provider rows; each row is today's form (auth, URL, model, key,
  probe). Add / delete live there, not on the identity. The identity form gains a provider
  picker and a model field (catalog from that row; empty model means the row's default). The
  session header's model badge becomes a picker: provider, model, and an "identity default"
  choice that clears the override. Changing it does not change the identity, the allow-list or
  the memories. No slash-command, no chat verb.

*Refuses*:

- Keying `turn.rs` on a global `provider()` now that a roster exists, or adding a second loop.

- **Session.** `StoredSession` writes `provider_id` / `model` only when set.
  `SessionStore::create_bound` writes an override in the same save as the record;
  `set_binding` does not bump `updated_at`. `AppState::set_session_binding` refuses during a turn,
  treats blank as absent, and checks the row. `Event::SessionUpdated` is boxed: the summary grew.
- **Errors.** `ProviderNotFound` (a stale row id) and `ProviderInUse { identities, sessions }`,
  both `E_INTERNAL` like their identity counterparts. Deleting `"default"`, an unknown id on an
  identity or a session, and clearing a CLI row's key are `E_INVALID_SETTING`.
- **IPC.** As the table above, plus: `settings_list_models` takes an optional `provider_id` to
  pick whose stored key asks (default `"default"`); a second OpenAI-compatible row would
  otherwise list with the default row's key.
- **UI.** `ProviderList` above `ProviderForm`; the form edits the selected row or a new one and
  carries the delete. `state/binding.ts` mirrors `resolve` for the header and the empty
  transcript. `ModelBadge` is a button opening a picker (provider, model, *Use identity default*),
  disabled while a turn runs; a dot marks an override.
